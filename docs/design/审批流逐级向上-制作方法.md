# 审批流「逐级向上」制作方法（可直接复制）

> 适用系统：卡迪高运营管理系统（前端 Vite + Express + MSSQL）
> 依据：直营标杆链已落地（flowNo=`AF-ZY-BX-001`，报销-门店组直营），本文档说明如何把同一套方法复制到其他单据类型（借款/预付款）与加盟、山东链路。

---

## 一、链路模型（先理解，再动手）

你要的效果：**用户在那个层级就提交，审批从他的上一级开始逐级向上；二级（督导）提交的单只由 3/4/5/6 级审；链路末端抄送出纳。**

直营标杆链路（Excel 第2行「门店组直营」）：

| Excel 级 | 角色 | 实现在审批步骤中的位置 | 说明 |
|---|---|---|---|
| 1级 | 门店组直营（发起层） | 无审批步骤 | 门店员工/店长提交 |
| 2级 | 督导组直营 | Step1 审批：区经组直营×督导 | 门店员工提交 → 督导先审；督导本人提交则跳过本级 |
| 3级 | 区经组直营 | Step2 审批：区经组直营×区经 | 督导提交 → 区经审 |
| 4级 | 运营总监直营 | Step3 审批：运营总监直营×运营总监 | 区经提交 → 运营总监审 |
| 5级 | 财务总监直营 | Step4 审批：财务总监直营×财务（跨组织） | 运营总监提交 → 财务审 |
| 6级 | 老板 | Step5 审批：老板（跨组织） | 财务提交 → 老板审 |
| 7级 | 出纳员（抄送） | 抄送：财务总监直营 + 出纳员 | 审批通过后可见 |

**核心机制：`initiatorRoles`（发起定位角色）**

- 每一级审批步骤可配 `initiatorRoles`（角色 code 数组），含义是：**申请人拥有其中任一角色时，本级不审他，从下一级开始**。
- 后端在创建审批任务时统一裁剪：取申请人命中 `initiatorRoles` 的**最高一级**，跳过该级及之前所有级，从下一级起审，并把 level 重排为连续的 1..N。
- 一条链路上所有级都不命中（如门店员工）→ 从第 1 级开始；裁剪后为空（如老板本人提交）→ 直接通过，不创建任务。

## 二、前置事实核对（用 SQL 查清楚你的组织/角色）

落地任何链路前，先核对以下 4 件事，避免审批人命中失败：

```sql
-- 1) 角色 code（本系统字典）
SELECT role_code, role_name FROM sys_role
WHERE role_code IN ('boss','ops_director','area_manager','supervisor','finance','staff','shop_manager');

-- 2) 目标组织及祖先路径（ancestors 决定组织线命中）
SELECT org_id, org_name, ancestors FROM sys_org WHERE org_id IN (2,3,9,16,32,37,25);

-- 3) 关键用户绑定到哪个组织（审批人自身组织必须命中 orgId 线）
SELECT ur.user_code, r.role_code, o.org_id, o.org_name, o.ancestors
FROM sys_user_role ur
JOIN sys_role r ON r.role_id = ur.role_id AND r.status=1 AND r.del_flag=0
LEFT JOIN sys_org o ON o.org_id = ur.org_id AND o.del_flag=0
WHERE r.role_code IN ('supervisor','area_manager','ops_director','finance','boss') AND ur.org_id IS NOT NULL;

-- 4) 申请人组织快照解析逻辑（与后端 resolveApplicantOrg 完全一致：TOP 1 ORDER BY ur.id）
SELECT TOP 1 o.org_id, o.org_name, o.ancestors
FROM sys_user_role ur JOIN sys_org o ON o.org_id = ur.org_id AND o.del_flag = 0
WHERE ur.user_code = '{申请人}' AND ur.org_id IS NOT NULL ORDER BY ur.id;
```

### 组织线命中的判定规则（后端 `isOrgInRange`）
`orgPath` 含 `/{orgId}/` 即命中。例如区经_陈万龙 path=`/1/3/16/45/` 命中 org16（区经组直营）但**不**命中 org2（老板）。**锚点组织选"各角色共同的组织线根节点"**：直营督导/区经个人组织都在`/1/3/16/`（区经组直营）线内，所以 Step1/Step2 都锚定 org16，用 roleCode 区分角色；跨部门角色（财务 org9、老板 org2、运营 org3）单独锚定。

### crossOrg（跨组织审批）何时用
`org` 类型审批人默认要求**申请人组织线也命中** orgId（防跨组织同名角色误批）。当审批人组织与申请人组织不在一条线上（如直营门店的财务是 `/1/9/`，门店是 `/1/3/16/.../`）时，必须给该审批人加 `crossOrg: true`，跳过申请人侧校验、只校验审批人自身组织与角色。直营链里 Step4（财务）、Step5（老板）需要；加盟链同样如此。

## 三、前端配置（审批流设计页操作）

在「费用报销 → 审批流配置」页新建流程时：

1. **流程类型**：选『报销』/『借款』/『预付款』（决定匹配 `paymentType`，一个类型可配多条+适用范围）。
   条件限定：一般留空（全局适用），按组织适用范围隔离加盟链。
2. **适用范围**：勾选组织（如直营：运营总监直营 org3 / 财务总监直营 org9 / 老板 org2）。保存后写入 `org_ids`；申请人组织线命中任一即适用，加盟（`/1/4/`）、山东（`/1/5/`）不命中。
3. **逐级添加审批步骤**（每级一个审批人配置项）：
   - 审批人类型选 **组织**，组织选锚点（Step1/Step2 选区经组直营、Step3 选运营总监直营、Step4 选财务总监直营并勾选『跨组织审批』、Step5 选老板并勾选『跨组织审批』）；
   - **角色**选对应角色（督导/区经/运营总监/财务/老板）；
   - 每级下方勾选**发起定位角色**（`initiatorRoles`）：Step1 勾督导、Step2 勾区经、Step3 勾运营总监、Step4 勾财务、Step5 勾老板——**这一步就是"哪层提交就从上一层继续审"的关键**。
4. **抄送**：在审批步骤区底部配置抄送，选 用户（可多选）或 组织（可多选）。本例抄送：组织=财务总监直营 + 出纳员；出纳员组织目前无成员时，抄送财务总监直营托底（ZY08001 可见），出纳入组（组织挂在出纳员下）后自动命中。
5. 保存。前端会把 `approvalSteps`（含 `initiatorRoles` 与 `crossOrg`）、`org_ids`、`cc_users`、`cc_orgs` 整体写入 `ApprovalFlow`。

> 页面新增能力（本轮已完成代码改造，直接可用）：审批人类型增加『组织』与『跨组织审批』勾选；每级新增『发起定位角色』多选；抄送编辑器 CcEditor 支持用户/组织多选；审批进度组件展示抄送区。

推荐用页面配置；如需脚本化（批量/复制链路），直接用随文模板：

- 阈值提醒：出纳员组织 `org25` 当前**无成员**，抄送落点是"财务总监直营（ZY08001）可见 + 出纳员组织命中（入组后自动可见）"。若要出纳本人收到，需先为该组织添加成员或改抄送用户。

## 五、加盟/山东链路复制指南

直营链用的是 org3/9/16/2；加盟/山东换锚点即可，机制不变：

| 链路 | 督导锚点 | 区经锚点 | 运营锚点 | 财务锚点 | 老板 | 适用范围 |
|---|---|---|---|---|---|---|
| 直营（已落地） | org16 区经组直营×supervisor | org16×area_manager | org3×ops_director | org9×finance(cross) | org2×boss(cross) | 3,9,2 |
| 加盟 | org18 区经组加盟×supervisor（督导绑定在 `/1/4/18/` 下） | org18×area_manager | org4 运营总监加盟×ops_director | org10 财务总监加盟×finance(cross) | org2×boss(cross) | 4,10,2 |
| 山东 | org20 区经组山东×supervisor | org20×area_manager | org5 运营总监山东×ops_director | org9 财务总监直营×finance(cross)（山东财务归属直营？需按实际） | org2×boss(cross) | 5,9,2 |

> 加盟/山东各组织的 org_id 与用户绑定请务必先用第二节 SQL 实测（尤其山东财务归属与出纳组织归属），再改模板。

**重要**：一个 `paymentType`（如 `报销`）下直营、加盟、山东是多条 `active` 流程并存，靠 `org_ids` 隔离：申请人组织线只命中其中一条的适用范围 → 只走那条。都不命中 → 走 `org_ids` 为空的历史兜底流程（若存在）。

## 六、验证清单（改完必测）

1. **入门**：门店员工提交 → 应生成 5 级任务，第 1 级可审批人是督导（区经不可批）。
2. **逐级向上**：督导提交 → 只生成 4 级（区经→运营→财务→老板），不再有督导级；区经提交→3 级；运营→2 级；财务→1 级；老板提交→直接通过，单据状态 approved。
3. **跨组织隔离**：加盟员工（如 105316）提交 → 不命中直营流程；加盟财务（JM02008）不能批直营财务级（组织线 `/1/10/26/` 不含 `/9/`）。
4. **抄送**：末级通过后，抄送人（出纳员组织成员/财务总监直营 ZY08001）在列表与详情可见该单据。
5. **推进**：每级有任意一人通过即可进入下一级（`level+1`）；末级通过自动置单据 `approved`；驳回置 `rejected` 并终止。

## 七、「单条统一流」方法（新推荐：一个单据类型只建一条流，覆盖全部部门）

> **适用前提**：系统已支持 `orgLevel` 审批人类型（按申请人组织链第 N 层动态展开）+ `initiatorRoles` 发起裁剪 + 组织 `crossOrg`。
> **结论先行**：**不需要按部门/业务线重复建流**。一条全局报销流（`org_ids` 为空 = 全局适用）即可让不同部门申请人自动落到各自的审批链，且审批任务天然按组织隔离、互不可见。已落地实例：`AF-GLB-BX-001`（报销-全局统一流）。

### 7.1 为什么能一条流覆盖全部部门

后端 `createApprovalTasks` 对 `orgLevel:N` 审批人的展开逻辑：

1. 取申请人组织快照 `orgPath`（如运营门店员工 `/1/3/16/45/46/47/`，数据 IT `/1/14/31/`）；
2. `orgPath.split('/')` 按段切分，`orgLevel:N` 取第 N 段组织（`segs[N-1]`）固化为审批人组织；
3. **超界丢弃**：组织链深度不足 N 段 → 该审批人丢弃，整级全丢自动跳级并重排 level；
4. **有效性兜底（本轮新增+修复）**：展开后若目标组织内**不存在持有对应角色的有效用户**，同样丢弃该审批人（如联营商组织内无 `supervisor` 角色）；全部审批人丢弃 → 单据直接通过，不卡单。**修复：以 `validityChecked` 开关为准**——只要有效性查询成功执行（即使结果为空集）即启用裁剪，避免"查询成功但无匹配角色"时保留死步骤卡单（详见 7.3.2）；
5. 各职能线命中各自的部门总监组织 → **天然按部门隔离**，不会串流。

### 7.2 统一流步骤 JSON 设计（报销-全局）

| Step | 审批人（approvers[]） | 角色 | initiatorRoles（发起定位角色） | 说明 |
|---|---|---|---|---|
| 1 | `orgLevel:5` | `supervisor` | `['supervisor']` | 运营线督导（数据/人事等线深度不足自动丢弃） |
| 2 | `orgLevel:4` | `area_manager` | `['area_manager']` | 运营线区经 |
| 3 | `orgLevel:2` × 6 条 | `ops_director` / `product` / `data_admin` / `hr` / `procurement` / `inspector` | 六类总监角色 | 各部门总监级：谁提交命中哪个线就审哪个线（2026-09 拆分后各线**总监保留原 code**，专员/职能走新 code 不进 initiatorRoles，由本线总监审） |
| 4 | `org:9` 财务总监直营 | `finance` | `['finance']` | 财务跨组织（crossOrg:true） |
| 5 | `org:2` 老板 | `boss` | `['boss']` | 老板跨组织（crossOrg:true） |

- `cc_orgs`（抄送）仍按需配：如直营报销 `[{org_id:9,org_name:'财务总监直营'},{org_id:25,org_name:'出纳员'}]`。
- `org_ids` 留空（存 NULL）= **全局兜底适用**；若现存多条全局流则取 `createdAt` 最新者。**旧的组织化流（设了 org_ids 的）会优先命中**，所以统一流落地时要先把旧流停用（`status='inactive'`），避免组织化旧流抢先命中直营员工而绕过统一流。已固化在历史任务上的快照不受停用影响。

#### 7.3.1 商品线角色拆分（商品专员 vs 商品总监，2026-09 实测通过）

**背景**：原 `product` 角色名为「商品总监/商品组」，商品组用户（org21/22 商品组直营/加盟的专员）与商品总监（org6/7/8）共用同一角色。商品专员提交报销时因持有 `product` 命中 Step3 的 `initiatorRoles` → 被误判为「商品总监本人」→ **跳过商品总监级**，直接生成 财务→老板 2 级任务，商品总监级被空过。

**拆分方案（已落地）**：

1. 新建角色 `merchandise`（商品经理/专员，role_name「商品经理/专员」，`default_data_scope=3`，role_id=20）；
2. 复制 `product` 的 46 条 `sys_role_menu` 菜单授权给 `merchandise`（按 portal_en+menu_en 复制，保证登录菜单不缩水）；
3. **迁移绑定**：org21/22 商品组 12 人（ZY02002~ZY02007 直营、JM02002~JM02005/JM02007/JM02010 加盟）`sys_user_role.role_id` 从 `product(12)` 改绑到 `merchandise(20)`；
4. **保留**：org6/7/8 三名商品总监（ZY02001/JM02001/SD02001）仍持 `product`，角色名改「商品总监」；
5. **统一流第 3 级配置不动**：`approvers` 仍含 `orgLevel:2 × product`（商品总监审）、`initiatorRoles` 仍含 `product`。**merchandise 不进 `initiatorRoles`**——否则商品专员（持 merchandise）提交时又会命中该级而被跳过总监级，与拆分目标相悖；迁移用户角色本身就是修复。

**拆分后端到端实测**：

| 申请人 | 拆分后实际审批链 |
|---|---|
| 商品专员 ZY02002（merchandise，org21） | **3 级：商品总监(org6,product)→财务(org9)→老板(org2)**（不再跳过总监级） |
| 商品总监 ZY02001（product，org6） | 2 级：财务→老板（本人提交跳过总监级，保持原语义） |
| 出纳（105322，finance，org25） | 抄送可见：单据进度 `/approval-task/source` HTTP 200，`cc_orgs=[org9财务总监直营, org25出纳员]` |
| 数据 IT（ZY04002） | 跨线隔离不破坏：my-pending 0 命中商品线单据；访问商品线单据进度 HTTP 403 |

**迁移 SQL 要点（幂等）**：

```sql

WHERE role_id=12 AND NOT EXISTS (SELECT 1 FROM sys_role_menu m2
  WHERE m2.role_id=@merchId AND m2.portal_en=sys_role_menu.portal_en AND m2.menu_en=sys_role_menu.menu_en);
-- 3) 迁移商品组用户（org21/22）绑定

-- 4) product 角色名收敛为「商品总监」
```

#### 7.3.2 其余合并角色拆分（财务/数据/人事/采购/稽查，2026-09 实测通过）

### 7.4 跨部门隔离（不串审批流）机制

1. **待办接口** `/approval-task/my-pending`：全表扫描 pending 任务后逐条 `isUserInApproversAsync` 二次过滤——数据/人事用户不持有运营线审批角色（supervisor/area_manager/ops_director），看不到运营单的待办；
2. **审批流进度接口** `/approval-task/source/:type/:id`（本轮新增鉴权）：只有**申请人本人、任一任务审批人、被抄送人**可见；数据/人事用户访问运营单据审批流 → HTTP 403；
3. **审批操作** `/approval-task/:id/approve|reject`：同样走 `isUserInApproversAsync`，非审批人 403；
4. **单据列表**：走 `resolveOrgScope` 组织数据权限（`data_admin` 与 `it` 为特权角色可看全量——IT 职责需要全量排查；`finance_staff`/`cashier`/`procurement_staff` 与源角色 `finance`/`procurement` 一致也在特权清单内，属既有设计，如需收紧由角色权限另行控制）。
